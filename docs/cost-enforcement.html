Cost enforcement research

Checked 2026-10-24 · installed Hermes Agent v0.19.0 (2026.7.20)

What we verified

Hermes LW now sets a per-task maximum runtime and a one-attempt limit when creating new tasks. In the installed Hermes version, Kanban supports --max-runtime and --max-retries. Hermes' dispatcher terminates a worker after it exceeds the selected runtime; the one-attempt failure limit blocks a timeout instead of automatically starting another try.

This does not cap dollars. Runtime length and provider spend are not interchangeable. The per-profile USD entries in Hermes LW remain planning metadata, and external CLI/gateway clients can bypass Hermes LW's saved profile allowlist.

Closest native protection: OpenRouter limited keys

OpenRouter can create a separate inference key with a hard USD limit. Setting limit_reset: null makes it non-resetting. Set include_byok_in_limit: true if BYOK usage should count. Creating the key needs an OpenRouter Management key; Management keys administer keys but cannot make inference calls. The created inference key is only returned once.

Sources: Create API key docs, Spend-control setup guide.

Scope: this is a hard cap for one key, so it can serve as a cumulative profile allowance if Hermes only uses that key. It is not a per-task budget. Any other provider key, environment credential, custom endpoint, or fallback can route around it.

Per-task caps across providers: a metering gateway

The strongest design is to put every Hermes model call through a local OpenAI-compatible gateway. Pass an authenticated task/session ID from Hermes' worker dispatcher to the gateway. Before each provider request, the gateway estimates worst-case request cost and reserves that amount against the task budget. It rejects requests when a reservation would cross the cap, then reconciles actual usage after the provider responds. Main model, auxiliary model, tool-model and retries must all use the same gateway.

LiteLLM Proxy already implements model routing, virtual keys and spend checks. Its docs say it estimates a request's max cost from the body and pricing, reserves the estimate, rejects before dispatch when the budget would be exceeded, and replaces the reservation with actual cost on response. Budgets require a database; its fail-closed setting rejects if it cannot verify authoritative spend.

Sources: LiteLLM budgets and reservations, Virtual keys.

Hermes LW does not yet deploy LiteLLM or route Hermes traffic through it. The integration must also strip direct provider credentials and refuse model requests when the gateway or pricing information is unavailable.

Recommended path

  1. Keep the runtime and retry safeguards already added for app-created tasks.
  2. Add opt-in OpenRouter key provisioning for a cumulative profile cap. Accept the Management key only for the create/update operation; store only the capped inference key in the selected profile.
  3. Detect Hermes capabilities before using upstream-only task fields. Never assume the installed CLI supports a current-main option.
  4. Prototype the LiteLLM gateway for real per-task limits. Require database-backed reservations, a worker task identity, no direct credential escape, and fail-closed behavior before enabling paid dispatch.
  5. Show actual usage, current reservations, cap remaining and pricing source separately from estimates.

See the complete source-linked report in docs/cost-enforcement.md.

Until an inference key cap or metering gateway is configured and verified, Hermes LW cannot guarantee that a task will stay below its displayed dollar budget.
